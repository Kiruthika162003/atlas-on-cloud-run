1What you will do

You shipped an AI product in four weeks. It works on your laptop. Now what happens when a hundred people open it at once?

In this session you take one working agent and move it to Google Cloud without rewriting it. The agent is Atlas, a map agent: you tell it where you are, and it finds three places worth the walk, describes each one from checked sources, and draws the route. You do not need to have attended the session where it was built. The finished app is in the repository.

2.2 How to read the dark boxes

Dark boxes show a terminal. A bright line after the green > is something you type, followed by Enter. Do not type the > itself. Grey lines are what the computer answers; yours may differ slightly.

Type one line at a time and wait for it to finish before typing the next. Every command in this guide is a single line, even when the page wraps it onto two.

4Set up Google Cloud

You need five things: a project, a billing account, your laptop signed in, four services switched on, and one database created. Each is a few clicks or one command.

4.1 Create a project

A project is a labelled box that holds everything you use on Google Cloud and the bill for it.

  1. Open console.cloud.google.com/projectcreate and sign in with your Google account. The first time, accept the terms of service.
  2. Type a project name, for example my-atlas.
  3. Under the name box there is a line that begins Project ID. Write it down. It looks like my-atlas-123456. The ID is what matters, not the name.
  4. Press Create and wait for the bell at the top right to show it is done.

4.2 Switch on billing

  1. Open console.cloud.google.com/billing.
  2. If you have no billing account, press Create account and follow the form. This is where the card goes. New accounts are usually offered free trial credit.
  3. Open console.cloud.google.com/billing/projects. Find your project in the list. If its billing account column is empty, press the three dots at the end of the row, choose Change billing, and pick your billing account.

4.3 Sign in from the terminal

You sign in twice, and they are different things. The first signs in you, for the gcloud commands. The second signs in programs on your laptop, so the container you run in step 2 can call Gemini without a secret key.

gcloud auth login
Your browser has been opened to visit: ...
You are now logged in as [you@gmail.com].

A browser tab opens. Choose your account and press Allow. Then tell gcloud which project to use:

gcloud config set project YOUR_PROJECT_ID
Updated property [core/project].
gcloud auth application-default login
Credentials saved to file: [...application_default_credentials.json]

The browser opens once more. Allow it again.

4.4 Switch on four services

On Google Cloud every service is off until you switch it on for your project. This session uses four.

ServiceWhat it does here
Cloud RunRuns your container, and starts more copies when traffic grows
Artifact RegistryStores the container image so Cloud Run can fetch it
FirestoreA database. It keeps the chats, so every copy of the app sees them
Vertex AIGives the agent the Gemini model

One command switches on all four. It takes about a minute.

gcloud services enable run.googleapis.com artifactregistry.googleapis.com firestore.googleapis.com aiplatform.googleapis.com
Operation "operations/acat.p2-..." finished successfully.

Prefer clicking? Open console.cloud.google.com/apis/library, search for each name in the table, open it, and press Enable.

It says billing must be enabled? The project from 4.1 is not linked to a billing account yet. Go back to 4.2, step 3.

4.5 Create the Firestore database

Switching Firestore on does not create a database. This does. A project gets one default database, and that is the one the app uses.

gcloud firestore databases create --location=us-central1
Waiting for operation to complete...done.

If it answers that the database already exists, your project already has one and you can carry on.

Prefer clicking? Open console.cloud.google.com/firestore, press Create a Firestore database, keep Standard edition and Native mode, choose the region us-central1, and press Create database.

6.1 The four changes that make the app ready for the cloud

The agents were not rewritten. The app file, atlas/app.py, has four small changes, each marked with a comment. Open the file and find them.

ChangeWhatWhy the cloud needs it
1Chats can be kept in FirestoreSeveral copies of the app run at once, and they must share what users said
2Every reply names the instance that sent itSo you can see scaling happen
3The port comes from the PORT settingCloud Run decides the port, not the app
4One log line per chat turnIn the cloud, logs are the only window into your app

Change 1 is the important one. It is six lines:

if os.getenv("ATLAS_SESSIONS") == "firestore":
    from google.adk.integrations.firestore.firestore_session_service import FirestoreSessionService
    sessions = FirestoreSessionService()
else:
    sessions = InMemorySessionService()

runner = Runner(agent=root_agent, app_name="atlas", session_service=sessions, auto_create_session=True)

The agent is handed a session service, the thing that remembers each chat. One setting decides whether that memory is inside the running program or in a database. You will flip that setting in step 8 without touching the code.

7Step 1: put the app in a container

On your laptop the app works because your laptop has the right Python, the right packages and the right files. A container image packs all of that into one file, so it runs the same way on any machine, including Google's.

ImageThe packed app. A file. You build it once. ContainerA running copy of the image. You can start many from one image. DockerfileThe recipe Docker follows to build the image.

7.1 Read the Dockerfile

Open Dockerfile. It is short, and every line is a step in the recipe.

FROM python:3.13-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

ENV GOOGLE_GENAI_USE_VERTEXAI=TRUE \
    GOOGLE_CLOUD_LOCATION=global \
    ATLAS_MODEL=gemini-3.8-flash \
    PYTHONUNBUFFERED=1 \
    PYTHONWARNINGS=ignore

CMD ["sh", "serve.sh"]
LineWhat it means
FROMStart from a small Linux that already has Python 3.13
WORKDIRWork in a folder called /app inside the image
COPY requirements.txt then RUN pip installInstall the packages. Doing this before copying the code means Docker reuses this slow step until the package list changes
COPY . .Copy the code in. The file .dockerignore lists what to leave out, such as .env
ENVSettings baked into the image: use Gemini through Vertex AI, and print logs straight away
CMDWhat to run when a container starts
No key in the image. Nothing secret is copied in. On Cloud Run the service signs its own calls to Gemini and Firestore. On your laptop you lend the container your sign-in for a moment (step 2).

7.2 Read serve.sh

Atlas is three programs: the places server, the description agent and the web app. The container starts all three. The first two stay private inside the container, and only the web app listens on the port that Cloud Run sends traffic to.

python mcp_server/server.py &
python description_agent/agent.py &

exec gunicorn --chdir atlas --bind :${PORT:-8080} --workers 1 --threads 16 --timeout 0 app:app

gunicorn is a web server made for production. --threads 16 lets one copy of the app talk to 16 users at the same moment. Remember that number; it comes back in step 7.

7.3 Build the image

The dot at the end means "use the Dockerfile in this folder". -t atlas names the image.

docker build -t atlas .

 => [internal] load metadata for docker.io/library/python:3.13-slim
 => [1/5] FROM docker.io/library/python:3.13-slim
 => [2/5] WORKDIR /app
 => [3/5] COPY requirements.txt .
 => [4/5] RUN pip install --no-cache-dir -r requirements.txt            185.4s
 => [5/5] COPY . .

The first build took a little over three minutes here, nearly all of it installing packages. Build again after changing only code and it takes seconds, because the package step is reused.

On a Mac with an M-series chip build with docker build --platform linux/amd64 -t atlas . instead. Cloud Run runs images built for that kind of processor.

10.1 Prove it is private

Paste your Service URL into a browser. You get Error: Forbidden. That is the service doing its job: every request your agent answers costs you money, so strangers should not be able to send them. From the terminal it is the number 403:

curl -s -o /dev/null -w "%{http_code}" YOUR_SERVICE_URL
403

On Windows PowerShell type curl.exe where this guide says curl.

10.2 Open it as yourself

This command opens a private tunnel from your laptop to the service and attaches your sign-in to every request. Leave it running in its own terminal.

gcloud run services proxy atlas --region us-central1 --port 8080
Proxying to Cloud Run service [atlas] in project [my-atlas-123456] region [us-central1]
http://127.0.0.1:8080 proxies to https://atlas-xniespgdxa-uc.a.run.app

The first time, it asks to install a small component. Answer Y. Then open http://localhost:8080 and ask a question. Same page as before, but this time the answer comes from Google Cloud.

When you are done looking, press Ctrl+C in the proxy terminal.

Who signs the calls to Gemini now? Not you. A Cloud Run service runs as a service account, an identity for programs. It has no password and no key file; Google Cloud vouches for it. That is why the image never needed a secret.

12Step 6: twenty users at once

One person asking one question tells you nothing about production. The load test sends twenty people at the same moment.

Each pretend user has a two-line chat. Neither line needs a map or a search, so the whole test costs a few cents:

Line 1"Hi, my name is Asha." Line 2"What is my name? Answer with the name only."

If the agent answers "Asha", it remembered. The script counts how many users were remembered, and which instances answered.

python loadtest.py YOUR_SERVICE_URL --users 20
20 users at once, answered by 1 instance
  0a04   ######################################## 40
remembered 20 of 20 users
a two-line chat took 9.6s at best, 12.6s in the middle, 41.6s at worst

One instance answered all 40 lines, and everyone was remembered. So far, so good.

Why only one instance? Because Cloud Run's default is to send up to 80 requests at a time to a single instance before it starts another. Twenty is well under eighty.

Is that a good default for an agent? Not really. A web page that returns in 20 milliseconds can share an instance with 79 others. An agent turn holds a connection open for many seconds while it waits on a model. And remember --threads 16 in serve.sh: this app can only work on 16 requests at once, whatever Cloud Run sends it.

13Step 7: tune concurrency and watch it scale

Two numbers control scaling. Concurrency is how many requests one instance takes at a time. Max instances is the ceiling on how many instances there can be.

Set concurrency low, so that twenty users need more than one instance, and cap the instances at five so the bill has a ceiling too:

gcloud run services update atlas --region us-central1 --concurrency 4 --max-instances 5
Done.
Service [atlas] revision [atlas-00003-jzr] has been deployed and is serving 100 percent of traffic.

Nothing was rebuilt. This is a setting on the service, and it took a few seconds. Now the same load test:

python loadtest.py YOUR_SERVICE_URL --users 20
20 users at once, answered by 3 instances
  5761   ################## 18
  3997   ########### 11
  0bda   ########### 11
turned away and asked again: 5 requests (HTTP 500)
remembered 6 of 20 users
a two-line chat took 19.9s at best, 38.8s in the middle, 82.9s at worst

Three things happened, and each one is a lesson.

13.1 It scaled

Three instances answered. Nobody started them; Cloud Run saw more requests than one instance was allowed to take and started more. This is the instance count for the whole test run, read from Cloud Monitoring:

In the console, the same picture is under Metrics, in the chart Container instance count.

13.2 Some requests were turned away

Five requests got an error first. Cloud Logging says why:

The request was aborted because there was no available instance.

A new instance needs a few seconds to start: fetch the image, start Python, start three programs. That is a cold start. During a sudden burst, a request can wait for an instance that is not up yet and be turned away with HTTP 429 or 500. The load test does what a real client should do: it waits three seconds and asks again, and counts how often it had to. Section 15 covers how to reduce this.

13.3 It forgot people

Only 6 of 20 users were remembered. Nothing crashed, and no error was shown for it. The users simply got a wrong answer. Here is why:

Asha:  "Hi, my name is Asha."   ──▶ instance 5761   (remembers Asha, in its own memory)
Asha:  "What is my name?"       ──▶ instance 3997   (has never heard of Asha)

Each instance kept its chats in its own memory. Cloud Run sends each request to whichever instance has room, so the second line of a chat often lands on an instance that never saw the first. The six who were remembered were lucky: both of their lines happened to reach the same instance.

This is the bug that only shows in production. On a laptop there is one copy of the app, so memory inside the program always works. The same code, scaled out, quietly loses conversations. An instance that is removed when traffic drops takes its chats with it too.

14Step 8: Firestore, so chats survive

The fix is to stop keeping chats inside the instance. Put them in a database that every instance reads and writes. The app is then stateless: any instance can serve any user.

The code is already there; it is Change 1 from section 6.1. Switch it on with one setting. No rebuild, no push.

gcloud run services update atlas --region us-central1 --update-env-vars ATLAS_SESSIONS=firestore
Done.
Service [atlas] revision [atlas-00009-vsz] has been deployed and is serving 100 percent of traffic.

Run the same load test again:

python loadtest.py YOUR_SERVICE_URL --users 20

15Choosing your own numbers

The settings in this guide were chosen to make scaling visible with only twenty users. For your own product, think about them like this.

SettingWhat it tradesA place to start for an agent
--concurrencyHigher: fewer instances and a smaller bill, but slower answers when one instance is crowded. Lower: faster, more instancesNo higher than the number of requests your server can really work on at once. Here that is the 16 threads in serve.sh
--max-instancesA ceiling on scale and on cost. Too low and users are turned away at busy timesEnough for your busiest expected moment, and no more. It also protects the model quota behind the agent
--min-instancesKeeps instances warm so nobody waits for a cold start. You pay for them all day0 while you are building. 1 when real users are waiting
--memory, --cpuBigger instances start faster and take more requests each, and cost more per secondWatch the memory chart under Metrics and leave some room above the peak
--timeoutHow long one request may runThe default is five minutes, enough for a long agent turn

Change any of them with the same command you used in step 7, for example:

gcloud run services update atlas --region us-central1 --concurrency 8 --max-instances 10

Then run the load test again and compare. That loop, change one number and measure, is what tuning means.

15.1 What else a real launch needs

  • Clients that retry. You saw requests turned away during a burst. Anything that calls your service should wait a moment and try again, as the load test does.
  • The model has limits too. Cloud Run can start instances faster than your Gemini quota grows. If the logs show 429 from the model, more instances will not help.
  • Someone to let in. The service is private. For real users you either put a sign-in in front of it or make it public on purpose with --allow-unauthenticated, knowing every request costs money.
  • Services you depend on. The map data comes from free OpenStreetMap servers that ask for light use. They are fine for a workshop. A product needs a paid map service or its own copy of the data.
  • A budget alert. Open console.cloud.google.com/billing/budgets and create one, so an email reaches you before a surprise does.

17Clean up, and what it costs

A Cloud Run service with no traffic runs zero instances and costs nothing for compute. The stored image and the stored chats are small, but there is no reason to leave them. Three commands remove everything this guide created.

Delete the stored chats:

python sessions.py --clear
20 chats stored in Firestore
All cleared.

Delete the service:

gcloud run services delete atlas --region us-central1
Deleting [atlas]...done.
Deleted service [atlas].

Delete the image repository:

gcloud artifacts repositories delete atlas --location us-central1
Delete request issued for: [atlas]
Deleted repository [atlas].

Answer Y when the last two ask you to confirm. To free the disk space on your laptop as well, run docker rmi atlas.

What you usedHow it is charged
Cloud RunFor the seconds instances spend handling requests. There is a monthly free allowance
Gemini on Vertex AIFor the text going in and out. A full map answer is about ten model calls
Google Search groundingPer search, on top of the model. Only full map answers use it, not the load test
Artifact RegistryFor stored images, per GB per month. One 90 MB image is within the free allowance
FirestoreFor reads, writes and storage. There is a daily free allowance, far above what a workshop uses
Cloud LoggingFor log volume, with a large monthly free allowance

To see what you actually spent, open console.cloud.google.com/billing, choose your billing account, and open Reports. Costs can take a day to appear.

The surest way to stop all charges is to delete the project: console.cloud.google.com/iam-admin/settings, then Shut down. Only do this if the project holds nothing else you need.
